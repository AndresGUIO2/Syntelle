# Streaming message inactivity

The [explicit Start and demo-time policy](stream-demo-limits.md) now precedes this behavior: arrival is static with the chosen background; production sessions have five minutes of active time and each visitor has 15 minutes accumulated. Local development disables those two caps through an explicit server setting. Inactivity pauses remain enabled and preserve any applicable remaining allowances.

The API pauses a render session after two minutes without a user message, including before the first message. Each new message starts another two-minute inactivity allowance. This replaces the earlier 30-second initial allowance. These are server-owned durations, checked by the existing one-second cleanup ticker, including for background tabs.

Switching tabs is not a pause or microphone-stop action. The active public player retains the same connection, reply and user-enabled capture while hidden, including a microphone permission/worklet setup that began before the switch. Returning to the tab neither starts another session nor replays input. Manual microphone shutdown, New chat, server inactivity/expiry, capture errors, transport cleanup and workspace disposal still release capture. Visibility does not reset the server inactivity clock or override browser/OS media suspension.

## Activity and pause

A fresh validated `message` or `speak` command, an accepted nonempty user turn, or a completed nonempty recognized transcript resets activity. Duplicate command submissions, unfinished/empty transcripts, silence, microphone PCM/activity/start/stop notifications, heartbeats, signaling, model output, playback, previews and appearance changes do not extend the deadline. Time is measured from user input, so an ongoing reply can be cancelled when the two-minute deadline arrives.

The final expiry check and message timestamp share the service mutex. A stale cleanup scan cannot pause a session after newer input has refreshed its deadline. The independent 30-second transport-loss cleanup remains in force and reconnecting does not reset the user inactivity clock.

Pausing removes the active session, cancels its conversation/provider context, closes recognition and sends `stop` to the private worker. It persists `paused` with `closed_at` and the reason `user inactivity`, then sends a bounded `paused` notice and closes the player transport. The browser releases media/microphone resources, preserves the visible transcript and shows **Resume**, with English and Spanish copy. The renderer process may remain running; this is session cleanup, not a cloud GPU shutdown or a monetary budget.

## Explicit resume

Resume requires a new authenticated `POST /api/v1/streams` with `resume_from` pointing to the paused stream. The server resolves this ID under the current principal, restores its existing conversation, rechecks admission/capacity and issues a fresh single-use player ticket. Paused records are reused without adding a schema or replaying a user turn/provider request. Both empty conversations and those with existing messages receive the two-minute inactivity allowance. Changing the conversation language requires **New chat**.

Closing persistence atomically marks accepted commands interrupted, so resume cannot interleave with half of a pause write. Late ordinary state updates cannot overwrite a closed pause. Simultaneous resume requests cannot replace an active session. Unknown/foreign paused IDs return the same not-found response.

Automatic transport recovery only reattaches to an existing active stream. If its lookup fails, recovery stops instead of allocating another renderer; this also covers a pause notice lost with the connection. A failed explicit resume retains the paused ID for another manual attempt. Changing interface language while paused does not restart transmission.
