## PostgreSQL accounting

Migration `002_demo_time.sql` adds `used_ms`, `lease_ms` and `lease_started_at` to existing streaming session records. Historical records start at zero without invented past usage. Session constraints bound spent plus reserved time to 300,000 ms.

Before any conversation/renderer work, allocation takes a PostgreSQL transaction advisory lock for the resolved principal. It sums every retained session's spent and reserved time, then grants the smaller of the session's remaining five minutes and the visitor's remaining 900,000 ms. Concurrent tabs, browser sessions and integration keys sharing an account cannot over-allocate. A final allowance shorter than five minutes is permitted. No allowance returns HTTP 429 before downstream work.

Each grant provides a server deadline and a matching cancellation context for conversation/provider work. The existing one-second expiry sweep stops rendering and notifies the player. Heartbeats, messages, reconnects and client timers cannot extend that deadline. Pausing or closing atomically charges elapsed server time up to the grant and releases its unused reservation. Resume does not reset either the session's spent time or the principal's total. Ordinary DELETE closes retained records rather than deleting their accounting.

If an API process disappears before settlement, startup conservatively charges its bounded outstanding reservation. Restart never restores spent allowance; failure can consume unused reserved time. No daily reset or public reset endpoint is introduced. The streaming coordinator remains a single API process; the budget lock does not make its existing startup/session routing safe for multiple replicas.

Identity means the existing account principal or anonymous visitor cookie. Account keys share the account balance. Cookie deletion or a different anonymous browser creates a different guest identity; this is not a durable per-person allowance. Guest usage is not automatically merged into a subsequently signed-in account.

The local per-visitor concurrent-session exception remains disabled through `SYNTELLE_STREAM_SESSION_LIMIT_ENABLED=false`. The owner subsequently disabled local demo-time limits through `SYNTELLE_STREAM_TIME_LIMITS_ENABLED=false` in Compose and `.env.example`. An absent setting or explicit `true` preserves production caps; invalid values fail startup. This is a server-owned switch, not a browser override.

Unmetered development sessions keep ordinary lifecycle records and an explicit `development-time-limits-disabled` event, with no time reservation or demo deadline. They bypass previously exhausted production allowance without resetting or consuming it. Pause/resume still restores conversation history. The read-only streaming status and session responses expose `time_limits_enabled`; the UI hides the 5/15-minute notice locally without opening a renderer to discover the policy. No schema change accompanies this exception. Existing inactivity, transport/provider safety bounds, authentication, admission rates and global renderer capacity remain in force. Stopping a worker session does not by itself stop a cloud GPU process or guarantee a monetary spending cap.
