# Local speech concurrency

The local Azure Speech provider previously held one `sync.Mutex` across each Dragon HD synthesis. Other conversations waited for the lock while their 60-second provider deadlines elapsed. A cancelled request could not leave that wait until the active call released the mutex. Two phrase workers per conversation could therefore add to the backlog, even though each turn retained ordered audio delivery.

The API now admits up to 50 active voice users per replica. A conversation holds one user slot while its microphone, reply generation or audio playback is active. Its simultaneous speech phrases share that slot. A direct speech request holds one slot until its response finishes. Idle conversation connections consume no voice slot. The 51st active user receives a capacity error before a speech reservation or paid synthesis; a slot becomes available when active work finishes, the microphone stops, playback ends or is cancelled, or the connection closes. This is an admission limit for current local capacity, not a claim that 50 complete video sessions have been measured.

`GET /api/v1/speech/status` reports `active_voice_users` and `max_active_voice_users` for the local API replica.

The provider uses a separate cancellable admission gate. Eight native syntheses may run simultaneously per API replica by default. `SYNTELLE_SPEECH_CONCURRENCY` accepts 1–32 for later tuning; it bounds active Azure calls within the 50 admitted users. Waiting requests retain their conversation cancellation and receive the full provider deadline only after admission. Cached speech returns before the provider gate. The existing input reservation still precedes a paid call, and failed or uncertain calls are not retried automatically. Voice, region, SDK version, audio format and native viseme handling are unchanged.

An earlier offline fixture completed 64 distinct simultaneous service requests before the 50-user admission limit was introduced. The current fixture verifies 50 users with eight provider calls active at once, plus rejection of a 51st user before ledger reservation and reuse of the released slot. An isolated PostgreSQL conversation check verifies microphone, completed playback, cancelled playback and microphone capacity rejection. Focused checks also cover cancellation while waiting and a queue wait longer than the provider deadline. The race checks and full Linux Speech SDK build passed. The local API is active with the 50-user limit and eight provider calls; its status reports `active_voice_users: 0` and `max_active_voice_users: 50` at idle. The native render worker reconnected with unchanged phase-93 assets and a 2 GiB memory limit. No live Azure synthesis, model call or paid retry was made for this change.

This verifies application scheduling only. Azure's actual Dragon HD throughput in Canada Central still needs a bounded live measurement. The gate is local to one API replica; it does not coordinate multiple cloud replicas. Render admission remains separate: the current local worker advertises ten sessions, while the Modal candidate allows two per container and multiple containers. Cloud admission remains at two pending a T4 qualification. None of these settings establishes fifty complete video sessions.

## Identical phrases during concurrent conversations

On October 26, four local conversations began together. One turn displayed a speech-preparation error after Gemini had emitted its first phrase. PostgreSQL showed no Azure synthesis failure for that turn: another conversation had reserved the exact same phrase, and its synthesis completed successfully shortly afterward. The second reservation saw the first operation in `started` state and returned an error instead of waiting for its result. Cancelling the affected turn then left its Gemini stream archived as failed before completion. This was an application cache-admission collision, not evidence of an Azure Speech throttle.

For an identical active phrase, the owner speech ledger now waits, with cancellation and the turn deadline, for that exact operation to finish. It reuses only a completed, validated audio result. A failed, cancelled or uncertain first attempt remains terminal for its waiters; no paid retry is launched. A different input using the same request key still fails immediately. An isolated PostgreSQL test covers both successful reuse and a failed first attempt, with one operation in each case; race checks and the pinned Linux Speech SDK build passed. The corrected API image is active locally. No paid provider call was made for this repair.
