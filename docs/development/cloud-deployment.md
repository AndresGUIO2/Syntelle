# Deployment preparation

Target origin: **https://app.syntelle.online**. Browser HTTP/WebSocket account and stream traffic uses its /api proxy. Integrations use the computed Azure API URL. Python uses its Azure URL with a separate service credential. PostgreSQL uses Azure private DNS. The renderer runs on Modal and sends WebRTC media to the browser, using TURN where needed.

This delivery adds local/cloud access modes, authenticated edge and processor boundaries, persisted worker startup allocation, optional short-lived TURN REST credentials, a native cloud worker lifecycle, Terraform and offline deployment fixtures. No cloud resources or GPU invocations are created by checks. Internet connectivity, actual Modal NVENC exposure and observed scale-to-zero require a subsequent bounded live acceptance; they are not established by offline tests.

## Prerequisites and secrets

Use the selected Azure subscription, existing Cloudflare zone, and selected Modal workspace. Authenticate Azure CLI with the intended subscription before running a plan. Application and infrastructure secrets must live in .deploy-private/config.json or CI secrets, never in source, build context, browser assets, screenshots or preparation evidence. Terraform state contains sensitive values: use private Azure Blob state with Entra authentication, locking and versioning. Bootstrap local state is also private and must be retained securely.

Pin providers through the checked-in lock files. AzAPI 2.13.0's bundled schema predates the documented stable 2026-07-01 API, so the two Express resources explicitly disable its embedded schema validation; Terraform validation is not ARM deployment validation. A live regional/quota preflight must precede provisioning. Do not silently replace Express with another environment type.

## Configuration

Copy deploy/config.example.json into .deploy-private/config.json and populate its fields. Set azure.subscription_id and azure.tenant_id to the intended Azure account; every plan/apply selects and verifies that account through Azure CLI. Foundation database_password and services.secrets are private inputs. Required application secrets: SYNTELLE_AUTH_SECRET, SYNTELLE_EDGE_TOKEN, SYNTELLE_PROCESSOR_TOKEN, SYNTELLE_RENDER_WORKER_TOKEN, SYNTELLE_MODAL_LAUNCH_TOKEN, SYNTELLE_DATABASE_URL and registry. Use independent random values of at least 32 bytes. SYNTELLE_TURN_SECRET is optional and required only when SYNTELLE_TURN_URLS is configured. Provider credentials are optional: absent providers remain disabled.

Runtime inputs include SYNTELLE_PACKAGE_HASH, optional SYNTELLE_TURN_URLS (comma-separated turn:/turns: addresses supporting TURN REST HMAC-SHA1), optional SYNTELLE_STUN_URLS, SYNTELLE_MODAL_LAUNCH_URL and the explicitly selected Gemini/Speech configuration. Cloud API and worker deployment can proceed without TURN; when configured, TURN signing secrets are never sent to browsers and credentials expire after 15 minutes. A shared deployment secret is used for worker access; allocation IDs must match the persisted, unexpired startup lease.

## TURN decision

Decision recorded October 23, 2026: TURN remains deferred to the medium term. Do not create a TURN key, configure provider credentials or enable TURN billing in the current deployment stage. Public deployment may use Cloudflare's free public STUN endpoint (`stun:stun.cloudflare.com:3478`) for direct ICE connectivity. STUN discovers public network addresses but does not relay media; sessions can still fail on restrictive NATs/firewalls until TURN is added. Cloudflare documents its public STUN service as free and unlimited: https://developers.cloudflare.com/realtime/turn/faq/.

The current runtime integration expects a TURN REST HMAC-SHA1-compatible service. Cloudflare Realtime issues temporary credentials through its server-side API, so using it will require an API credential-provider adapter and a Terraform-managed TURN key before wiring its ICE server configuration. Keep the Cloudflare API key on the Go API server and pass only short-lived ICE credentials to the browser. Media remains browser-to-renderer, through TURN only when direct connectivity fails.

Azure defaults: reuse the configured existing resource group (currently `rg-syntelle`), and create new deployment resources in Canada Central. The resource group itself is read as data; existing resources in it are not adopted into Terraform state. PostgreSQL is version 18, B1ms/32 GiB, with seven-day backups, no HA, a private database subnet and DNS; Container Apps uses Express VNet egress. API and processor each have zero-to-one replicas. ACR Basic and PostgreSQL retain baseline charges even when application/GPU compute is idle. Storage, registry, networking, external relay egress and provider usage must be budgeted separately; there is no monetary hard cap.

Modal defaults: us-east, T4, one container, two stream capacity, no warm/buffer containers, two-second idle container scale-down window and no retries. Worker exits five seconds after the last stop and immediately after control disconnect. A never-used worker exits after its startup grace. Its function timeout is 30 minutes. The API stops admitting new sessions after 24 minutes, leaving current five-minute sessions time to finish before the function deadline.

## Commands and rollout

Retail reference checked October 22, 2026 for Canada Central: PostgreSQL B1ms compute is USD 0.0185/hour (about USD 13.51 at 730 hours); ACR Basic is USD 0.1666/day (about USD 5/month). Together they start around USD 18.5–18.6/month **before** the 32 GiB database storage, chargeable backup storage, networking and usage-based application/Modal/provider charges. This is a baseline floor, not a total deployment quote; subscription grants and negotiated rates can differ. Sources: [Azure retail pricing API](https://prices.azure.com/api/retail/prices), [PostgreSQL pricing](https://azure.microsoft.com/en-us/pricing/details/postgresql/flexible-server/).

From the repository root, `python deploy.py` defaults to offline checks. `python deploy.py plan --stack bootstrap|foundation|services` produces a plan only. On Windows, `./deploy/run.ps1 -Stack bootstrap` or `./deploy/run.ps1 -Stack all` runs an explicit apply; the latter prompts securely for the Cloudflare token and verifies Modal authentication through the active CLI profile or the two CI token environment variables. The Modal token is never copied into the repository or echoed by the preflight. The Azure CLI subscription and private config are checked before Terraform runs. `python deploy.py apply --stack bootstrap|foundation|services|all` is also available for environments where provider credentials are already set; it explicitly authorizes resource creation and does not ask for a second confirmation. Save any manually exported plan only under `.deploy-private/`.

The services apply uses Terraform parallelism 1 because concurrent Container App creation in the same VNet can collide on Azure's Service Association Link lease. If one app succeeds and the other fails with that lease conflict, wait briefly and rerun only `./deploy/run.ps1 -Stack services`; Terraform will retain the successful app and retry the missing one without rebuilding or reapplying foundation resources.

On a later all-mode rollout, keep an already published Worker custom domain attached while the Azure services and Modal launcher update. Only the first deployment, which has no launcher URL yet, stages the services with `publish_frontend=false`. If a previous interrupted rollout left the Cloudflare Worker or custom domain absent from Terraform state, rebuild the frontend and recover them with `./deploy/run.ps1 -Stack services` after checking the current private config contains the desired release hash, pinned images and Modal launcher URL. This avoids repeating foundation, image pushes and GPU deployment just to restore the frontend.

1. Fill config.bootstrap with a new storage account name and the deployment principal's object ID. Run `python deploy.py plan --stack bootstrap`, review it, then explicitly apply that stack. Bootstrap creates the private state storage and registers the Azure providers required by foundation. Those subscription-level registrations have `prevent_destroy`; AzureRM automatic provider registration is disabled so a plan does not change registration state. Its local state stays in `.deploy-private/bootstrap.tfstate`. Do not delete or overwrite another state account.
2. Apply foundation, then use terraform output -json foundation to populate services.foundation. Collect the registry password privately.
3. Build API and renderer with the root context (source-only `.dockerignore`); build processor with `services/processor` as its context. Push to the foundation registry and record immutable repository digests in services.images (api/processor) and SYNTELLE_RENDER_IMAGE. Never forward the full root environment to the renderer. Preserve active package/source hashes; do not regenerate preparation assets.
4. Set the application database URL with TLS verification (sslmode=verify-full), percent-encoded credentials and the computed database FQDN. Initialize a new syntelle database; never import local evidence/history. Apply services with publish_frontend=false.
5. Use `uv run --with-requirements deploy/requirements.lock python -m deploy.modal_configure .deploy-private/config.json` with modal.image and modal.api_origin filled from actual outputs. This creates the three dedicated Modal secrets, deploys through the official CLI and returns the actual launch URL. It does not invoke the GPU function. For individual manual deployment, use the same locked environment and `modal deploy deploy/modal_app.py`; never guess the launch URL.
6. Reapply services to wire the launcher and publish the Vue player at `https://app.syntelle.online`. Publication requires the actual Modal launcher URL and at least one STUN or TURN endpoint. STUN-only publication does not imply TURN relay coverage or completed live-media acceptance; validate direct ICE, CUDA/NVENC, cancellation and scale-to-zero separately, then add TURN in the medium term if target networks require relay.

The GitHub checks workflow never creates real resources: Terraform tests use mocked providers, including one mocked apply to verify ARM-derived endpoint outputs. Application checks use fixture providers, isolated PostgreSQL, portable Go tests, processor authorization and ten focused desktop/mobile browser cases. The deployment workflow is dispatch-only, uses the production GitHub environment and consumes SYNTELLE_DEPLOY_CONFIG. Azure authentication uses one AZURE_CREDENTIALS JSON secret containing clientId, clientSecret, subscriptionId and tenantId; Cloudflare and Modal use their separate token secrets.

Selecting stack=all (or `python deploy.py apply --stack all`) automates foundation, image build/push, Azure services, Modal secrets/deployment, launcher URL discovery and final wiring in that order. Its preflight verifies Cloudflare, Modal, Azure database, package, profile and credential inputs before the foundation apply. The profile must be reviewed, explicitly owner-accepted and bound to the exact native package; incomplete candidates stop before resource creation. A configured STUN or TURN endpoint is required when publishing the frontend; TURN URLs and a compatible TURN secret are required only when choosing TURN. With a token that has Zone Read permission, it resolves and verifies the exact `syntelle.online` zone and owning account, then stores those non-secret IDs in the private config. CI also requires SYNTELLE_RENDER_BUNDLE_URL (a short-lived HTTPS Azure Blob signed URL) and SYNTELLE_RENDER_BUNDLE_SHA256. Supply an approved ZIP containing `assets/` and `performance.json`; set config.modal.assets to `.deploy-private/release/assets` and config.performance_profile to `.deploy-private/release/performance.json`. The downloader verifies SHA-256, limits archive size and rejects traversal/symlinks before extracting privately. The archive must contain only the chosen native export/profile, never evidence, conversations or environment files. Uploading this protected input is a future operator action; no archive has been uploaded during preparation. Individual stacks remain available for review/recovery. No deployment workflow is triggered automatically by pushes.

When this checkout has a local `.env` selecting `SYNTELLE_PACKAGE_HASH`, all-mode apply rejects a different hash in the private deployment config before cloud authentication. This catches an archived release that otherwise passes its own manifest/profile checks. The explicit `--allow-inactive-release` flag is reserved for intentional all-mode rollback; it does not bypass exact package/profile validation or owner acceptance. Update the private assets, performance profile and hash together to publish a newer accepted release. CI without a local `.env` continues to use its explicit approved release archive and hash.

The checked-in dependency hashes are in deploy/requirements.lock. All-mode performs a read-only PostgreSQL region/version/SKU check before provisioning and rejects incomplete credentials/assets. State bootstrap remains an explicit prerequisite. The frontend is not published by default; enable `services.publish_frontend` only when the selected zone, assets, Modal launcher and STUN/TURN configuration are ready.

## Failure, recovery and rollback

An admitted stream returns 201/starting while startup runs. Startup is serialized in the API and protected by a PostgreSQL singleton lease before the one POST to Modal. Ambiguous results are not retried. Restarted APIs wait for an existing lease to expire rather than automatically duplicate GPU spend. Startup failures close streams and release admission; users can explicitly start again. Existing five-minute sessions, fifteen-minute visitor allowance and two-minute inactivity remain enabled in cloud mode. Direct API calls still require account/key authorization after ingress admission.

The initial maximum of one API replica is mandatory because session coordination and request counters remain process-local. Do not increase it without shared routing/admission. Restore previous immutable image digests and the prior Modal app version for rollback; drain/close current sessions first. Keep database schemas/data and state; prevent_destroy protects the database. Never use destroy as a rollback.

Legacy local mode remains the default and retains loopback-only control and reconnect behavior. Cloud mode never enables the uncapped owner endpoints. No local service rebuild, owner database modification or active character installation is performed by this preparation; PostgreSQL verification uses disposable isolated fixtures.

## Preparation verification

Verified without cloud credentials or paid calls: formatting/validation for all three Terraform stacks; mocked Express, replica, private PostgreSQL and computed endpoint checks; API unit tests; isolated PostgreSQL startup coalescing, ambiguous-outcome/restart recovery, cancellation and reservation cleanup under the race detector; native worker control authentication/disconnect and virtual-clock idle cleanup; Modal import/process fixtures; processor authorization; edge proxy cookies, redirects, errors, WebSocket passthrough and spoofed headers; public frontend type/build checks and ten focused desktop/mobile browser cases, including guest/account fixtures and reconnection without another allocation.

The older backend-player browser suite currently expects a removed text-start button in the concurrently updated microphone interface, so it did not pass unchanged. Deployment browser checks are isolated in `deploy/browser.playwright.config.ts`; this preparation does not claim that the older full suite or live cloud acceptance passed. Local sanitized verification records live under `.tools/deploy-prep/`; private deployment configuration/state and renderer export downloads are excluded from these records.
